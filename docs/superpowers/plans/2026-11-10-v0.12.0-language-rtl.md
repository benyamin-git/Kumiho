# v0.12.0 Language and RTL — Implementation Plan

**Spec:** `docs/superpowers/specs/2026-11-10-v0.12.0-language-rtl-design.md`
**Date:** 2026-11-10
**Status:** Approved

## Order

The engine setting lands first because every client reads it. The GUI
controller then publishes structured state before the web catalog grows, so no
screen has to parse English. Android follows the same rule at its own boundary.
The Persian UI review gate comes before release preparation.

## Global constraints

- Go 1.27.1, dependencies vendored; builds and tests must work with no network.
- Control protocol v1 stays byte-compatible. The `language` field and the new
  GUI projection fields are additive; no existing envelope changes.
- The engine stays OS-free. OS language detection and Android locale plumbing
  live in the clients or the platform seam, never in `internal/engine`.
- TUI and CLI stay English. They may display the new engine key as English
  data; they gain no translation layer and no language picker.
- Persian is formal/neutral. VPN stays Latin; tunnel = تونل, proxy = پروکسی,
  relay = رله, kill switch = قطع اضطراری.
- Persian digits and Jalali dates. IPs, ports, versions, email addresses,
  country/city names, server names, proper names and raw engine details stay
  Latin/English.
- Engine errors show a Persian summary and action. Raw engine details, logs,
  diagnostic facts and copied reports stay English.
- Vazirmatn v33.003, four static weights (400/500/600/700), used only when the
  effective language is Persian. English keeps the system font.
- Android `minSdk 26`, `targetSdk 36`, `compileSdk 37.2`; no new Gradle
  dependency. System surfaces (notification, tile, widgets, TV channel) use
  the effective language.
- Full RTL mirroring: rail right, navigation order, directional icons,
  progress and charts. Flags, logos and the power button stay unmirrored.
- Commit style `type: lowercase imperative summary`; one logical change per
  commit. Never push, tag or publish without an explicit request.
- Every commit leaves the Go gate green:

      make lint && make test && go test -race -count=1 ./... && make build && \
        GOOS=windows GOARCH=amd64 go vet ./... && \
        GOOS=windows GOARCH=amd64 go build ./... && \
        GOOS=android GOARCH=arm64 go build ./...

- Changes under `android/`, `mobile/` or `internal/platform/android/` also run:

      make android-test

  and, when the emulator work is in scope:

      make android-emulator-test          # phone AVD kumiho-api36
      make android-tv-emulator-test       # Google TV AVD

- GUI verification uses the dev harness on `0.0.0.0:7407` and the visual
  capture script. There is no Playwright job in CI; the capture is a local
  review tool.

The spec's `assumed` details D26–D55 are binding defaults for this plan unless
the implementation finds a concrete blocker. A blocker is reported before the
affected task is changed, not silently worked around.

## 2. Engine `language` setting

**Files**

- `internal/settings/settings.go`
- `internal/settings/settings_test.go`
- `internal/api/api.go`
- `internal/api/compat_test.go`
- `internal/engine/engine.go`
- `internal/engine/controller_test.go`
- `internal/cli/settings.go`
- `internal/cli/settings_test.go`

**Interfaces**

- `settings.Config.Language string` with TOML key `language`; one of
  `system`, `en`, `fa`; default `system`.
- `settings.State.Language *string` with JSON key `language,omitempty`.
- `effectiveConfigLocked` applies a stored value only when it is one of the
  three valid values; an unknown stored value resolves the effective language
  to `system` (D28), even if the config file carries another value.
- `SetOverride("language", value)` validates the enum, writes
  `State.Language`, and returns the existing bad-request shape for an invalid
  value. `ClearOverride("language")` removes it. `OverriddenKeys()` includes
  `language` when set.
- `api.SettingsView.Language string` with JSON key `language`, populated by
  `engine.settingsView` from the effective config.
- `ApplySetting` needs no engine-specific branch; it already routes through
  the settings store. Do not add a TUI picker or any translation.
- CLI: add `language` to `cliSettingKeys` and `settingTextValue` (returning
  `view.Language`), so the existing `kumiho settings get|set|reset language`
  path accepts `system|en|fa` with English output. No CLI prose changes.

**Tests**

- File/default config is `system`; invalid TOML value is rejected by
  `Validate`; a stored invalid state value resolves to `system`.
- Override round trip: set `fa`, settings view reports `fa`, `overridden`
  contains `language`, reset restores the file value.
- Invalid `settings_set` value is a bad request and leaves the prior value.
- `SettingsView` JSON includes `language`; an old fixture without the field
  still decodes. Update `api/compat_test.go` with the additive-field case.
- TUI tests that render `SettingsView` keep compiling and show the English
  key/value; no translation is added there.
- CLI `settings get language` prints `language = <value>`; `settings set
  language fa` and `settings reset language` emit the existing
  `SettingsSetPayload`; an invalid value reaches the engine and returns the
  normal bad-request error in English.

**Verify**

    go test ./internal/settings ./internal/api ./internal/engine ./internal/ipc \
      ./internal/daemon ./internal/gui ./internal/tui ./internal/cli
    make lint

## 3. GUI prefs cache and language projection

**Files**

- `internal/gui/prefs/prefs.go`
- `internal/gui/prefs/prefs_test.go`
- `internal/gui/prefs/prefs_windows.go`
- `internal/gui/prefs/prefs_other.go`
- `internal/gui/controller.go`
- `internal/gui/controller_test.go`
- `internal/gui/mock/mock.go`
- `internal/gui/host_windows.go`

**Interfaces**

- `prefs.Prefs.Language string` with TOML key `language`; the cached
  **effective** language (`en` or `fa`), empty on first run. Normalize any
  other value to empty.
- `prefs.SystemLanguage() string` returns `fa` only when the OS UI language is
  Persian, otherwise `en`:
  - Windows: `GetUserDefaultUILanguage` primary language id `0x29` (Persian)
    maps to `fa`; every other value maps to `en`.
  - Linux/harness: parse `LC_ALL`, `LC_MESSAGES`, then `LANG`; a `fa`/`fa_IR`
    primary tag maps to `fa`, otherwise `en`.
- `gui.Options.Language string` is the cached effective language for the first
  snapshot. `gui.Options.SystemLanguage string` is the resolved OS language
  (`en`/`fa`) and is injectable in tests.
- The controller keeps `language string` and exposes:
  - `State.Language string` (`json:"language,omitempty"`) — effective `en|fa`.
  - `State.SystemLanguage string` (`json:"system_language,omitempty"`) — raw
    OS resolution, needed by the `system` preview in the picker.
- `resolveLanguage(pref, system string) string`: `fa` → `fa`, `en` → `en`,
  anything else/`system` → `system == "fa" ? "fa" : "en"`.
- `loadSettings` success recomputes the effective language from
  `SettingsView.Language` and the seeded system language. A change publishes
  the new snapshot; the JS layer switches live.
- Host startup seeds both options from `prefs.Load()` and
  `prefs.SystemLanguage()`: `Options.Language` is the cached effective value
  when non-empty, otherwise the resolved system language. The host keeps
  `gui.toml` as a first-paint cache only; the engine setting remains
  authoritative.
- `prefs_set` accepts `language` (`en|fa`; empty clears the cache) and saves it.
  A language-only save does not reload the page.
- `mock` seeds `system`, `language: "en"` so the harness has deterministic
  first paint.

**Tests**

- `prefs` round trip and normalization of unknown language values; system
  language parser cases (`fa_IR.UTF-8`, `en_US.UTF-8`, empty, `LANG` fallback).
- `resolveLanguage` table: system/fa, system/en, explicit fa, explicit en,
  empty preference.
- Controller: settings load with `language: fa` publishes `fa`; explicit `en`
  on a Persian system publishes `en`; a later settings change republishes.
- Host `prefs_set` persists the cache and leaves the theme path untouched.

**Verify**

    go test ./internal/gui/... ./internal/settings ./internal/api
    make lint
    GOOS=windows GOARCH=amd64 go build ./...

**Commit:** `feat(gui): cache and project the language choice`

## 4. GUI structured notices and raw values

**Files**

- `internal/gui/controller.go`
- `internal/gui/controller_test.go`
- `internal/gui/state_hooks_windows.go`
- `internal/gui/update.go` (only if a code/param is missing)
- `internal/gui/mock/mock.go`

**Interfaces**

- `Notice` becomes additive:

      type Notice struct {
          Code    string         `json:"code,omitempty"`
          Params  map[string]any `json:"params,omitempty"`
          Message string         `json:"message,omitempty"` // English fallback
          Tone    string         `json:"tone,omitempty"`
          Expires *time.Time     `json:"expires,omitempty"`
      }

- Keep `Message` exactly as today. Every existing `setNotice`/`newNotice`
  call keeps its English text for old clients, logs and tests.
- Add one stable code per message site. The convention is
  `<surface>.<action>.<outcome>`, for example:
  - `dashboard.connect.failed`, `dashboard.disconnect.failed`,
    `dashboard.refresh.failed`, `dashboard.location.saved`
  - `locations.load.failed`, `locations.ping.done`, `locations.favorite.saved`,
    `locations.recents.cleared`, `locations.locked.hidden`
  - `settings.saved`, `settings.reset`, `settings.relay.ok`,
    `settings.relay.rejected`, `settings.relay.unreachable`,
    `settings.update.available`, `settings.update.current`,
  - `account.signed_in`, `account.sign_out.failed`,
    `account.add.failed`, `account.removed`
  - `logs.subscribe.failed`, `diagnostics.cleanup.done`,
    `diagnostics.service.failed`
- Params carry raw values, not preformatted English: counts as numbers,
  latency as a number, email/URL/host/status as strings, durations as epoch
  seconds where the JS can format them.
- Add a single helper:

      func (c *Controller) setNoticeCode(slot noticeSlot, code string,
          params map[string]any, msg, tone string, ttl time.Duration)

  `setNotice` stays for external host messages without a code.
- `StatusView` keeps every formatted field and adds raw fields:
  - `State string` (`st.State`; the JS maps `state.<code>` and falls back to
    `Label`).
  - `Since int64`, `TokenExpires int64`, `QuotaResetUnix int64`.
  - `RatesUp float64`, `RatesDown float64`, `TotalsUp int64`,
    `TotalsDown int64`.
- `ServiceState` adds `Code string` with the stable values `running`,
  `stopped`, `start_pending`, `stop_pending`, `paused`, `not_installed`,
  `unknown`; `State` stays the English word.
- `LoginView` adds `ErrorCode string` when the engine supplies a code. The raw
  `Error` string stays for the details block.
- `UpdateInfo` already carries raw `Current`/`Latest`/`URL`; notices use
  `settings.update.*` codes.
- `RelayTest` already carries `OK`, `Status`, `LatencyMS`, `Error`; notices use
  the codes above and numeric latency.
- Doctor checks stay technical English. Only the surrounding labels, actions
  and status words are translated.

**Tests**

- Representative tests assert `Code` and `Params` for: connect failure,
  location saved, setting saved/reset, relay OK/rejected/unreachable, update
  available/current, signed-in, sign-out failure, logs subscribe failure,
  cleanup done.
- Existing tests that assert English `Message` continue to pass.
- `StatusView` raw fields match `api.Status`; formatted fields unchanged.
- `ServiceState.Code` mapping table.
- A JSON snapshot test confirms the new fields are omitted when empty and
  present when set, so old clients see no change.

**Verify**

    go test ./internal/gui/... ./internal/api
    make lint
    GOOS=windows GOARCH=amd64 go build ./...

**Commit:** `feat(gui): emit structured status and notice codes`

## 5. GUI i18n foundation and shell

**Files**

- `$GUI/i18n/en.json` (new)
- `$GUI/i18n/fa.json` (new)
- `$GUI/js/i18n.js` (new)
- `$GUI/js/app.js`

- `$GUI/css/app.css`
- `internal/gui/web/server.go`
- `internal/gui/web/server_test.go`
- `internal/gui/web/i18n_test.go` (new)
- `internal/gui/i18n_test.go` (new; dynamic key families)
- `internal/gui/web/assets.go` (embed list, if explicit)
- `internal/gui/host_windows.go`
- `internal/gui/prefs/*` from task 3

**Interfaces**

- Catalogs are flat dotted-key JSON objects. English is the source of truth;
  Persian has the same key set.
- `i18n.js` exports:
  - `initI18n(lang)` — loads English as fallback, then the active catalog.
  - `t(key, params)` — active → English → key; replaces `{name}` placeholders.
  - `tp(key, count, params)` — plural helper only where a count is grammatical;
    Persian uses the same form for singular/plural in the catalog.
  - `formatNumber`, `formatDate`, `formatDateTime`, `formatBytes`,
    `formatDuration` — `fa-IR` uses Persian digits,
    `fa-IR-u-ca-persian` for Jalali dates; `en` uses `Intl` defaults.
  - `setLanguage(lang)` — updates `<html lang dir>`, dispatches
    `kumiho:languagechange`, re-applies `data-i18n` text.
  - `currentLanguage()`.
- Initial language order: `?lang=fa|en` (capture/dev override), then the
  injected `<meta name="kumiho-language">`, then `en`. The server injects the
  meta tag from `Server.SetLanguage` at render time.
- `index.html` adds `<!--kumiho:language-->` in `<head>` and
  `class="app-booting"` on `<body>`. `app.css` hides the shell until
  `app.js` removes the class; this prevents an English flash before the
  Persian catalog loads.
- `index.html` keeps the theme marker as the first head element before every
  stylesheet. The language marker sits beside it and expands to a single
  `<meta>` tag.
- `server.Server` gets `SetLanguage(lang string)` alongside `SetThemeCSS`.
  `handle` calls `injectLanguage` and `injectTheme` in one render path. The
  injected value is restricted to `en|fa`; anything else becomes `en`.
- Shell labels move to `data-i18n` keys; `app.js` applies them after catalog
  load. `router.js` exposes a re-render hook used by `app.js` on language
  change; the current route is re-rendered in place.
- When a controller snapshot changes the effective language (including a
  change made by the CLI/TUI), `app.js` applies it and sends
  `prefs_set {language: <effective>}` so the next first paint uses it. Local
  Settings/onboarding changes do the same.
- The host calls `server.SetLanguage` from the cached effective language
  before the first navigation. The harness uses `?lang=fa` for captures.
- Vazirmatn `@font-face` declarations live in `app.css` with
  `font-display: swap`; `initI18n("fa")` adds a preload link for the four
  WOFF2 files. English never references the family.
- Copy the four WOFF2 files to `$GUI/fonts/` with lowercase names
  (`vazirmatn-regular.woff2`, `vazirmatn-medium.woff2`,
  `vazirmatn-semibold.woff2`, `vazirmatn-bold.woff2`). The third-party copy
  stays canonical; the static copy is what `go:embed` serves.

**Catalog test**

`internal/gui/web/i18n_test.go` reads the embedded catalogs and:

- requires identical key sets in `en.json` and `fa.json`;
- requires identical `{placeholder}` sets for each key;
- rejects empty values;
- scans `$GUI/js/**/*.js` and `$GUI/index.html` for `t("…")`,
  `tp("…")`, and `data-i18n="…"` and requires each literal key to exist;
- allows declared dynamic prefix families (`state.`, `settings.`, `notice.`)
  whose suffixes are checked against the controller's raw state/setting/code
  tables in a `internal/gui` test, not by the literal scan;
- rejects a key that is neither referenced literally nor covered by a
  declared dynamic prefix, so dead strings are removed rather than
  accumulating.

**Other tests**

- Server `SetLanguage` injection: valid `fa`, invalid `de` → `en`, and the
  marker is replaced exactly once.
- Theme injection still works with the language marker present.
- Existing server tests continue to pass; the CSP remains `default-src 'self'`
  and the injected meta tag needs no nonce.

**Verify**

    go test ./internal/gui/web ./internal/gui/...
    make lint
    make build-web
    scripts/dev-gui-web.sh start
    # open http://127.0.0.1:7407/?lang=fa#/dashboard and check shell/nav only

**Interfaces**

- `Settings.language: String = "system"` at the end of the data class;
  `EngineJson.settings` reads `language` with a `system` default.
- `AppPrefs` adds `language: Flow<String>` and `setLanguage(value)` with key
  `language`. Empty means "no cached choice"; the engine setting is the
  source of truth.
- `LanguageRepository`:
  - `effective: StateFlow<AppLanguage>` where
    `enum class AppLanguage(val tag: String) { ENGLISH("en"), PERSIAN("fa") }`.
  - `preference: StateFlow<String>` (`system|en|fa`).
  - `ready: StateFlow<Boolean>` / `awaitReady()` once the cached preference
    and system locale have been read.
  - `setPreference(value)` normalizes to `system|en|fa`, persists the
    preference and immediately updates `effective` (system resolution uses
    the current OS locale).
  - `syncEngine(value)` records the engine's preference and derived effective
    language in the cache, without clobbering a newer local choice.
  - `localizedContext(base: Context): Context` uses
    `createConfigurationContext` with `setLocale` and `setLayoutDirection`.
  - `resolve(pref, system)`: same rule as the GUI.
- `AppContainer` starts the repository, collects the prefs flow, and when the
  engine becomes available reads `settings()` once to `syncEngine`. Failures
  keep the cached/system value.
- `KumihoApp` (in `ui/App.kt`) collects `effective`, builds the localized
  context, and provides:
  - `LocalContext` = localized context,
  - `LocalConfiguration` = localized configuration,
  - `LocalLayoutDirection` = `Rtl` for Persian, `Ltr` otherwise.
  The rest of the Compose tree is unchanged and continues to use
  `stringResource`.
- `MainActivity` keeps the splash until both the stored theme and the
  language repository are ready (`awaitReady()`), so a Persian user never
  sees an English flash before the first composition.
- `KumihoTheme` accepts the `AppLanguage` (or reads the provided layout
  direction) so the font family can be chosen in task 13.

## Risks and mitigations

- **Translation volume (700 Android keys, several hundred GUI keys).**
  Catalogs are added screen-by-screen; parity tests fail on a missing key.
  The review gate catches tone and truncation. The glossary is the single
  vocabulary source.
- **RTL regressions in custom layouts.** Logical-property audit, explicit
  unmirror list for flags/logo/power, phone and TV RTL tests, and full
  captures at the minimum window size.
- **First-paint flash or wrong language.** Body hidden until the active
  catalog loads; cached effective language injected before navigation;
  engine state reconciles live without a reload.
- **Engine setting vs. GUI cache drift.** Engine remains authoritative;
  every settings load recomputes effective language and rewrites the cache.
  The cache only serves the first paint.
- **Android system surfaces stale after a switch.** One language-change fan-out
  updates the notification, channels, tile, widgets and TV channel; the
  emulator check covers process-death persistence.
- **Jalali conversion errors.** Pure Kotlin converter with JVM tests at
  Nowruz and a leap-year boundary; no ICU dependency.
- **Font licensing or unsupported format.** OFL committed, checksums
  recorded, WOFF2 for the GUI and TTF for Android. WebView2 supports WOFF2
  and Android supports TTF.
- **Mixed-direction text (IPs, emails, versions inside Persian).** Isolate
  with `direction: ltr; unicode-bidi: isolate` (CSS) and
  `LayoutDirection.Ltr`/`UnicodeBidi.Isolate` (Compose); review captures.
- **Protocol compatibility.** Only new optional fields; `api/compat_test.go`
  covers the old fixture without `language`.
- **Release filename change breaks stable links.** Stable aliases are
  uploaded alongside every versioned primary; `install-release.sh` continues
  to read `SHA256SUMS`.
- **TUI/CLI accidentally translated.** No TUI/CLI task touches strings; the
  only change they see is the additive English `language` field. The CLI
  `settings` command can read/set it, as D40 requires, with English output.
- **Rollback.** Set `language = en` or `system`; no data migration exists.
  Code rollback is safe because the setting and all projection fields are
  additive and older clients ignore them.
