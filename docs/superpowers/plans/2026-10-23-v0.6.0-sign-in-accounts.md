# Kumiho v0.6.0 — Sign-in and Accounts Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the single password-only session with a browser-first PKCE
sign-in, up to five named Firefox accounts, account selection/rotation, and a
real quota poller, with full parity across the daemon, CLI, TUI, Windows GUI
and Android app.

**Architecture:** A new `internal/webauth` package owns PKCE, the one-shot
`127.0.0.1` loopback listener, and the browser `login/verify` exchange. The
engine owns the flow lifecycle so the daemon, Windows GUI, CLI/TUI and the
in-process Android app share one implementation. Accounts move from
`tokens.json` to `accounts.json` v2 (maximum five), while `tokens.json`
remains a rollback copy. Rotation is a pre-connect selection step, and quota
polling runs beside the existing pass renewal with backoff.

**Tech Stack:** Go 1.27.1 (stdlib only for the new auth/accounts code),
Bubble Tea TUI, hand-written WebView2 GUI, Kotlin/Compose Android app
(compileSdk 37.2, targetSdk 36, minSdk 26), AndroidX Browser 1.10.0.

**Spec:** `docs/superpowers/specs/2026-10-23-v0.6.0-roadmap-design.md`
(approved, commit `600d1db`).

## Global Constraints

- Supported targets: Ubuntu 24.04, Windows 11 amd64, Android 8.0+
  (arm64-v8a/armeabi-v7a). Every daemon/CLI/TUI/GUI change must cross-build for
  Linux and Windows; Android app changes must pass the Android gate.
- The engine stays OS-free. Browser platform names come from
  `platform.Provider.Name()` (`linux`, `windows`, `android`); no new
  `runtime.GOOS` branch in `internal/engine` or `internal/webauth`.
- Protocol v1 stays additive and byte-compatible for old clients. Never change
  the meaning of an existing type, envelope field or JSON field. New commands
  and fields are optional to old readers.
- Accounts: maximum five, unique by case-folded email, stable random IDs,
  `accounts.json` mode `0600`, atomic writes via `settings.WriteFileAtomic`.
  Labels default to the email; a user-entered label is trimmed, must be 1–64
  visible characters and must contain no control characters. No password and no
  `authPW` is ever persisted; `authPW` stays in memory only while an
  unblock-code retry is possible.
- Browser sign-in: PKCE S256, 128-character base64url verifier, loopback
  `127.0.0.1:0`, one-shot callback, five-minute timeout, callback HTML only.
  No `state` query parameter (see Ruling R1).
- Browser tokens have no refresh token. An expired browser token or a Guardian
  401 marks `browser.reauth_required`; it is never converted silently to a
  password account and never refreshed with an empty refresh token.
- Rotation is opt-in (`account_rotation=false`), threshold default `10` and
  range `1–50`. It runs before `Connect` only. Manual account switching or
  removing the active account while connected is refused with “disconnect
  first”; there is no mid-session switch. Quota ties break by least recently
  used. Skips are visible as an account notice.
- `logout` remains the global sign-out and clears every account. Per-account
  removal is `accounts_remove` / `kumiho accounts remove`.
- `quota_poll_minutes` defaults to 15 and is validated `1–1440`. Polling never
  tears down the tunnel; 401 marks re-auth and stops that poller, 429 means
  remaining `0`, and other errors retry with exponential backoff.
- Android: Custom Tabs via `androidx.browser:browser:1.10.0`.
  `usesCleartextTraffic` stays `false`; a network-security-config exception
  permits cleartext only for `127.0.0.1` and `localhost`. Browser strings are
  English only, matching `values/strings.xml`.
- TUI stays English. CLI output stays machine-friendly (`--json` where the
  command already has it).
- Every commit leaves `make lint && make test` green. Do not bump
  `version.Version`, `androidVersionName`, `CHANGELOG` release headings or tags.

## Review Focus

These are the five inputs/failure modes most likely to bite a user and are not
fully exercised by the happy-path task tests. Each is pinned to a task test:

1. **Headless or browserless sign-in.** A Linux server or a Windows session
   with no default browser must show the URL, time out cleanly after five
   minutes, and leave the previous session untouched. Test in Tasks 5 and 7.
2. **Account limit and duplicate email.** Adding a sixth account, or re-adding
   an existing email at the limit, must not corrupt `accounts.json` or drop the
   active session. Test in Tasks 3 and 4.
3. **Rotation with unknown/exhausted/re-auth accounts.** Rotation must never
   pick an exhausted or re-auth account, must name every exhausted account in
   the terminal error, and must not start a dead tunnel. Test in Task 6.
4. **Rollback and corrupt state.** A pre-v0.6 `tokens.json` must keep working,
   a corrupt `accounts.json` must not delete it, and an old client must still
   read the synchronized active token. Test in Tasks 3, 4 and 7.
5. **Android browser return/cancel/process death.** Back from Custom Tabs,
   cancellation, or a browserless device must leave the screen recoverable and
   must not leave an orphan loopback listener. Test in Task 11.

## Implementation Rulings

The spec is approved. These are the only places where the plan resolves a
spec ambiguity or makes an implementation choice that differs from a literal
sentence. **R1 and R2 need explicit approval at this gate; reject either and
the plan changes before code.** R3–R6 are implementation details consistent
with the spec.

- **R1 — No `state` parameter in the browser URL.** The spec’s own URL
  construction (step 3) omits `state`; the Mozilla reference client does not
  send or echo one. PKCE plus a one-shot random loopback port plus a
  five-minute timeout is the security boundary. The test asserts the URL has
  no `state` key. A `state` we cannot verify would be theater and would break
  the real flow.
- **R2 — `tokens.json` is a live rollback copy after migration.** The spec
  says migration leaves the original untouched. This plan leaves it untouched
  during migration, then rewrites it on the first login/switch/refresh/remove
  so an old client sees the active account. Global logout removes it. Without
  this, a rollback would silently sign the user into the first migrated
  account, and logout would leave a stale token behind. If rejected, keep the
  original bytes forever and document that rollback shows the first account.
- **R3 — `logout` is global; removal is per-account.** “Sign out” in every
  existing client keeps its contract (clear everything). The account list gets
  a separate remove action; removing the active account selects the most
  recently used remaining account, or signs out when none remains.
- **R4 — No switching while connected.** `accounts_use`, removing the active
  account, and any `login_start`/`accounts_add_start` that would change the
  active account return a “disconnect first” error while connected or
  connecting. Re-authenticating the active account is allowed. Rotation is
  the only automatic account change and happens before the tunnel is
  established.
- **R5 — Browser token expiry is authoritative.** The verify response’s token
  is parsed with `guardian.JWTExpiry`; if the token has no `exp`, expiry is
  `0` (unknown) and the first 401 marks re-auth. No refresh token is invented.
- **R6 — Account IDs are random, not FxA UIDs.** A 12-byte crypto-random hex
  ID avoids leaking the FxA UID into file names, logs and UI actions. The UID
  remains an entitlement/display field, not an identifier.

### Command families (not a deviation)

The spec names two families. They share one engine state machine but are
different protocol names so clients can express intent:

- `login_start|status|cancel` — sign in the active account.
- `accounts_add_start|status|cancel` — add or re-authenticate an account.
- `accounts_list`, `accounts_remove`, `accounts_use`,
  `accounts_set_rotation` — account-list surface.
- `accounts_update` — additive command required by editable labels; the spec
  lists label editing but not a wire name. Payload `{id, label}`.

Label interpretation (not a wire deviation): the add flow has no label field,
so re-adding an existing email replaces tokens/method but preserves a custom
label; `accounts_update` is the explicit path that replaces it. This is how the
plan applies the spec’s “replaces its tokens and label” without silently
resetting a user’s rename.

`login_email`, `login_password`, `login_2fa`, `account` and `logout` stay for
old clients.

- [ ] **Step 3: Implement the package**

Implement exactly these decisions in `internal/webauth/webauth.go`:

- `New` defaults: `BaseURL = "https://vpn.mozilla.org"`,
  `Timeout = 5 * time.Minute`, `Now = time.Now`, `Rand = rand.Reader`,
  `HTTP = http.DefaultClient`; reject an empty `Platform` in `Start` with
  `errors.New("webauth: platform is required")`.
- PKCE: 96 random bytes, base64url without padding (128 chars). Verifier is
  that string; challenge is
  `base64.RawURLEncoding.EncodeToString(sha256.Sum256([]byte(verifier)))`
  (43 chars).
- `Start`: `net.Listen("tcp", "127.0.0.1:0")`, `http.Server` on a fresh
  `http.ServeMux`, serve in one goroutine. Build the URL with path
  `/api/v2/vpn/login/<Platform>` and query keys in this order:
  `code_challenge`, `code_challenge_method=S256`, `user_agent`, `port`,
  `utm_medium=vpn-client`, `utm_source=kumiho`. Do not send `state` (R1).
- Handler: GET only; if `error` is present, send that error once; if `code` is
  empty, return HTTP 400; otherwise send the code once. Write a minimal
  `text/html` page: “Kumiho sign-in complete. You can close this tab and
  return to Kumiho.” A duplicate callback gets the same page but is ignored.
- `Wait`: select the code, `ctx.Done()`, the flow timeout, or `Cancel`.
  Exchange with `POST <BaseURL>/api/v2/vpn/login/verify` body
  `{"code":code,"code_verifier":verifier}` and the platform user agent.
  Retry up to five attempts on HTTP 406, calling `Solver.Solve` at most four
  times; if the solver is nil, return the 406 error. Limit the response to
  1 MiB.
- Parse `{"user":{"uid":...,"email":...,"displayName":...},"token":"..."}`.
  `uid` may be a string or a number. Require a non-empty token and a non-empty
  email; a response missing either is a fixed “missing user data” error and
  stores nothing. Set `ExpiresAt` with `guardian.JWTExpiry(token)`. Close the
  listener after `Wait` returns, success or failure.
- `Cancel` is idempotent and unblocks `Wait`.
- Never log the code, verifier or token.
