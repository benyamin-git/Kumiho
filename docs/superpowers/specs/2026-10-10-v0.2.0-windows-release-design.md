# Kumiho v0.2.0 — Windows Release + Hygiene — Design Spec

**Status:** Draft
**Date:** 2026-10-10

## Objective / why

Kumiho v0.1.0 is a working Linux client, and the 2026-10-10 multiplatform-core
refactor made the engine platform-pluggable with a Windows provider stub, a
transport seam and OS-aware paths. v0.2.0 turns that groundwork into the first
non-Linux release: a full-parity **Windows 11 client** (Wintun TUN, Windows
service, named-pipe IPC, TUI/CLI) plus the hygiene fixes deferred from the
refactor. A Windows user must be able to install, log in, run a full tunnel
with DNS and kill switch, and uninstall cleanly — with CI, tests and docs to
match, and with zero change to Linux behavior.

## Success criteria / definition of done

1. One `kumiho.exe` (windows/amd64) serves service, CLI and TUI modes; `make
   build-windows` and the CI `windows-latest` job (vet, tests, build, smoke)
   are green.
2. The `kumiho` Windows service installs via `install.ps1`, runs as
   LocalSystem, auto-starts at boot, honors autoconnect (default ON,
   remember-last-state), recovers from crashes, and uninstalls cleanly
   (`-Uninstall [-Purge]`).
3. Full tunnel on Windows 11 amd64: Wintun adapter (`foxy0`, 10.8.0.2/32, MTU
   8500), traffic through the Fastly edge via the unchanged engine, exit check
   passes, IPv6 blackholed.
4. DNS parity: adapter-scoped DNS points at the local listener on the tun
   address; DoH-through-tunnel, custom DNS and truncation behavior identical
   to Linux; no system-wide DNS settings touched.
5. Kill switch: WFP dynamic filters block non-tunnel traffic while on;
   LAN/exclude-CIDR exceptions honored; cleanup on start/stop; the crash
   caveat is documented and mitigated by service recovery + start-time cleanup.
6. TUI/CLI full parity over the named pipe with the `kumiho` group ACL;
   control protocol v1 (newline JSON) unchanged; `shutdown` restricted to
   administrators (Linux root-only parity).
7. Hygiene: `internal/dns` Start/Stop race fixed; CI actions on current majors
   (checkout v6, setup-go v7); stale comments/wording cleaned; netmon test
   assertions strengthened; transport Close-removal and nil-PeerUID paths
   covered; Android path error handling fixed.
8. Docs: README, docs/install.md, docs/manual.md, docs/troubleshooting.md,
   docs/usage.md and PLAN.md carry Windows content; new AGENTS.md,
   CHANGELOG.md, docs/windows-testing.md; NOTICE carries the wintun.dll
   license note.
9. Tag `v0.2.0` triggers a release workflow that builds linux/amd64,
   linux/arm64 and windows/amd64 zips (binary, wintun.dll, install script,
   licenses) and creates the GitHub release.
10. The committed manual E2E checklist (docs/windows-testing.md) is executed
    on a real Windows 11 box before the tag.

## Scope

### In scope

- `internal/platform/windows`: real Provider — Wintun device, routes, IPv6
  blackhole, interface DNS, WFP kill switch, link watching, default-route
  probe, paths, control endpoint.
- Windows IPC: `go-winio` named-pipe transport (byte-mode, newline JSON),
  SDDL ACL with a local `kumiho` group, admin check for `shutdown`.
- Windows service host: `x/sys/windows/svc` integration in the same binary,
  LocalSystem, auto-start, recovery, start-time cleanup.
- `install.ps1` (install / `-Uninstall` / `-Purge`), portable release zip.
- Makefile targets, `windows-latest` CI job, tag-triggered release workflow.
- Hygiene fixes listed in criterion 7.
- Docs pass and the three new documents; wintun.dll + license committed under
  `third_party/wintun/`.

### Non-goals (explicitly out)

- Android and other Linux backends; Windows arm64; MSI; code signing; split
  DNS/NRPT; preserving existing sessions across connect; winget/scoop
  manifests; auto-update; GUI/tray; per-app split tunneling; persistent WFP
  filters; any change to the control protocol, engine behavior, or Linux
  mechanisms.

## Architecture

The multiplatform core already froze the seams; v0.2.0 fills in the Windows
implementations without reshaping the engine.

- **Platform provider** (`internal/platform/windows`): implements the frozen
  `platform.Provider`. `OpenDevice` creates a Wintun adapter and exposes it as
  `io.ReadWriteCloser` (ring-buffer pumps); `NetConfig` applies/removes routes,
  interface DNS, IPv6 blackhole and the WFP kill switch; `WatchLinks` surfaces
  interface changes (IP Helper notifications, with polling as fallback);
  `HasDefaultRoute` uses `GetBestRoute2`; `BypassDialer` is plain (no SO_MARK
  equivalent — the kill switch permits the service's own traffic by process);
  `Paths`/`ControlEndpoint` return the D19 locations; `ChownControlEndpoint`
  is a no-op (pipe ACLs are set at creation).
- **IPC transport** (`internal/ipc`): a Windows `Transport` over `go-winio` —
  byte-mode pipe, newline-delimited JSON v1, SDDL restricted to LocalSystem +
  Administrators + the `kumiho` group; peer authorization reads the pipe
  client's token SID (admins-only `shutdown`), replacing UID checks.
- **Service host**: the same binary detects SCM context
  (`svc.IsWindowsService`) and runs the daemon under `svc.Run`; `install.ps1`
  registers it (auto-start, recovery-on-crash). Foreground `kumiho daemon`
  stays available for development.
- **Networking parity**: routes and DNS live in the Windows provider, mirroring
  the Linux mechanisms one-for-one (kill switch ↔ WFP filters, `resolvectl`
  ↔ `SetInterfaceDnsSettings`, policy routing ↔ default route + WFP, `SO_MARK`
  ↔ WFP service-process permit). The documented divergences: existing sessions
  may reset on connect; the kill switch is process-scoped (dynamic WFP session).
- **Distribution**: `third_party/wintun/` (committed DLL + license + checksum);
  `install.ps1`; `make build-windows`; release zips; CI windows job; tag-driven
  release workflow. New dependencies vendored (`go mod vendor`) so builds stay
  offline: `github.com/Microsoft/go-winio` (MIT),
  `golang.zx2c4.com/wintun` (MIT). No cgo.

Global constraints (carried into the plan verbatim): zero Linux behavior
change; Go 1.27.1; control protocol v1 byte-compatible; engine untouched;
provider seam consumed as-is (additive-only if unavoidable); deps vendored;
every task ends green (`make lint`, `make test`, `go test -race -count=1
./...`, `make build`, Windows/Android cross-builds).

## Risks + rollback

| Risk | Mitigation |
| --- | --- |
| `golang.zx2c4.com/wintun` frozen since 2023 | Vendored and pinned; thin binding; a maintained fork or syscall shim is a drop-in fallback |
| WFP dynamic session dies if the service crashes | Service recovery restarts it; start-time cleanup + re-apply; documented caveat |
| Existing sessions reset on connect | Accepted, documented (D10); exclude_cidrs + allow_lan cover LAN/Tailscale-like cases |
| wintun.dll redistribution terms | Unmodified, side-by-side, license text shipped; no embedding/memmod |
| Hosted-runner driver behavior unproven | CI limited to build/vet/tests; real-hardware E2E checklist gates the tag |
| Windows-specific bugs invisible to Linux CI | windows-latest job + committed E2E checklist + doctor parity checks |
| Rollback | v0.2.0 is additive; Linux untouched; `install.ps1 -Uninstall -Purge` removes all Windows state; revert the tag/release if fatal |

## Dependencies / ordering

- External: Wintun 0.14.1 DLL (committed), `go-winio`, `golang.zx2c4.com/wintun`,
  `x/sys/windows/svc` (already in x/sys), Windows 11 amd64 test hardware.
- Ordering: hygiene fixes early (independent); platform provider → transport →
  service host → installer → CI/release → docs; E2E checklist last before tag.
- Spec and plan are committed before any implementation task starts.
