# Kumiho v0.6.0–v0.12.0 Roadmap and v0.6.0 "Sign in and accounts" — Design Spec

**Status:** Draft
**Date:** 2026-10-23
**Scope:** Seven-release roadmap. Detailed design only for v0.6.0.

## Objective / why

The full feature set requested for the next major version — browser authentication,
multi-account rotation, region resilience, honest location data, DNS privacy,
Android polish, smart routing, desktop polish and Persian/RTL — is too large,
too risky and too hard to verify as one release. This spec splits it into seven
independently shippable chunks. Each chunk has its own spec and plan gate; only
v0.6.0 is designed in detail here.

v0.6.0 is the foundation: it replaces the fragile email/password-only sign-in
with a browser flow that handles captcha, TOTP and unblock codes, stores a
Guardian token safely, and introduces a multi-account store. That store is what
makes quota polling, account rotation and every later account surface possible.
Language support is deliberately last because it must translate the final UI,
not a moving target.

## Success criteria / definition of done

### Roadmap

1. Seven releases ship in the order below, each independently usable and
   independently verifiable.
2. Every release has its own approved spec and implementation plan before code
   starts. Later chunks are not implemented early.
3. A release may depend only on earlier releases listed in its "Depends on"
   row; no forward dependencies.
4. Existing settings, control-protocol v1 payloads and user data keep working
   across the roadmap. New fields and commands are additive.
5. Language support ships last (v0.12.0) and covers the Windows GUI and Android
   only; TUI and CLI stay English.
6. No release is tagged, pushed or published without an explicit request.

### v0.6.0

1. Browser sign-in works on Linux, Windows and Android: it opens Mozilla's
   Firefox Accounts page, completes captcha/TOTP/unblock there, returns through
   a loopback callback, and stores a Guardian token.
2. The first sign-in asks browser or password and remembers the choice; the
   password flow remains available everywhere, including headless CLI/TUI.
3. The password flow supports TOTP and unblock codes in addition to email 2FA.
4. Up to five accounts can be stored without ever storing a password; the
   Account screen lists them, shows the active one, adds, removes, renames and
   re-authenticates them.
5. `account_rotation` is opt-in and runs before connect only: if the active
   account is below `rotation_threshold` (default 10%), the engine selects the
   best eligible account, skips expired/re-auth accounts with a notice, and
   stops with a clear error only when every account is exhausted.
6. `quota_poll_minutes` finally does what it says: while connected, quota is
   refreshed on that interval without reconnecting or killing the tunnel.
7. A single-account `tokens.json` installation migrates to `accounts.json` v2
   without losing the session; the original token file remains as a rollback
   copy for one release.
8. The control protocol stays v1 and byte-compatible; new account/login
   commands and status fields are additive.
9. CLI, TUI, Windows GUI and Android expose the account surface; TUI labels stay
   English.
10. The Go gate (`make lint`, `make test`, race tests, Linux builds, Windows and
    Android cross-builds) and the Android gate (`make android-test`) pass. No
    physical-device acceptance is required for v0.6.0.
11. README, AGENTS.md, CHANGELOG, `docs/usage.md`, `docs/android.md`,
    `docs/gui.md`, `docs/manual.md` and `PLAN.md §13` describe the shipped
    behavior and the ToS risk.

### v0.6.0 — Sign in and accounts

**Goal.** Make sign-in work for every Firefox Accounts configuration, and make
multiple accounts a first-class, safe concept.

**In scope**

- Browser sign-in through Mozilla's PKCE flow on Linux, Windows and Android.
- Loopback callback owned by the engine; clients only open the returned URL.
- Guardian token storage, expiry parsing and re-authentication on 401/expiry.
- Password fallback with TOTP and unblock-code support.
- `accounts.json` v2 with migration from `tokens.json`; five-account cap.
- Account labels, active account, add/remove/re-auth, rotation toggle.
- Before-connect quota rotation at a configurable threshold; expired accounts
  are skipped with a notice.
- `quota_poll_minutes` polling while connected.
- Additive IPC commands and status fields; CLI/TUI/GUI/Android surfaces.
- Documentation and ToS warning.

**Non-goals**

- No relay, 451 handling, server-list filtering, ping changes or Fastest.
- No DNS, blocklist, routing, widget, no-AAAA, roots or auto-update work.
- No language support.
- No mid-session rotation and no automatic password fallback.
- No captcha-solving service and no password storage.
- No physical-device acceptance for this release.

**Acceptance.** The Go and Android gates pass; mock FxA/Guardian/loopback tests
cover every login step; rotation and migration have table-driven tests; the
control protocol round-trips through an old client fixture.

### v0.7.0 — Region and location truth

**Goal.** Make blocked regions understandable and location data honest.

**In scope**

- HTTP 451 classified as terminal; one automatic retry through a configured
  control-plane relay; clear settings hint after the retry.
- User-supplied HTTPS relay with optional bearer token, host allowlist for FxA,
  Guardian and Remote Settings, no request logging, and a Test button.
- Cloudflare Worker relay template under `contrib/relay-worker/`.
- Server list: live Firefox version, JEXL subset (`versionCompare`, `country`),
  `filter_expression`, `locked`; hide locked by default and reveal them with
  `allow_locked`.
- Real-delay ping through the tunnel to `vpn.mozilla.org:443`, 30-minute cache,
  Ping all and a selectable Fastest location.
- Favorites and recents in the Locations screen, shared engine state.

**Non-goals.** No DNS/blocklist/routing work, no Android widget, no auto-update,
no localization.

**Acceptance.** Go gate; fixture tests for JEXL and locked records; mock relay
tests for 451/allowlist/auth; ping-cache tests; no live leak test.

### v0.8.0 — DNS privacy

**Goal.** Give users control of the resolver and block ads/trackers without
intercepting TLS.

**In scope**

- Custom DoH endpoint accepting a hostname or IP; hostname bootstrap through
  system DNS once per session; pinned IPs; fail closed.
- AdGuard preset alongside the existing providers.
- StevenBlack unified hosts bundled, weekly refresh with last-good cache,
  NXDOMAIN answers, exact-and-subdomain allowlist.
- DNS-tamper test and dual-family exit probe in Diagnostics.

**Non-goals.** No direct routing, no geosite/geoip data, no Android widget, no
language support. Blocking is DNS-only; no TLS interception.

**Acceptance.** Go gate; mock DoH tests including bootstrap failure; blocklist
parser/refresh/allowlist tests; Android gate for the settings surface.

### v0.9.0 — Android polish

**Goal.** Close the Android parity gaps before routing lands.

**In scope**

- 1×1 connect toggle and 2×1 status+toggle widgets, sharing state with the Quick
  Settings tile; immutable PendingIntents.
- Suppress AAAA answers in the in-tunnel resolver; no FakeDNS.
- Default Android to the 25 s keepalive profile; no wake lock.
- Merge bundled GlobalSign R46/E46 roots with the system pool for edge, control
  plane and DoH; never replace system roots.

**Non-goals.** No smart routing, no desktop changes, no language support.

**Acceptance.** Android JVM/lint/emulator gate; Go gate; resolver tests for AAAA;
widget state tests; no physical acceptance.

### v0.10.0 — Smart routing

**Goal.** Send selected countries, domains and CIDRs outside the tunnel without
opening a leak.

**In scope**

- Bundle all-country v2fly domain lists (MIT) and geoip data (CC-BY-SA-4.0);
  NOTICE attribution; weekly refresh; last-good cache; fail closed.
- Direct routing on Linux (nftables/policy routing) and Windows (routes/WFP),
  with the kill switch permitting only the configured direct CIDRs.
- Android 13+ `excludeRoute`; Android 8–12 keeps per-app split with a clear
  note.
- Domains resolve through strict DoH inside the tunnel; matching IPs route
  direct; IPv6 stays blackholed and direct routing is IPv4-only.
- Custom domain/CIDR lists and the Routing screen with Direct routing,
  Blocklists and Custom lists groups.
- Linux network-namespace leak test in CI: direct traffic stays direct and
  tunneled traffic never leaks.

**Non-goals.** No IPv6 direct routing, no Windows/Android live leak test, no
system-proxy automation, no language support. Windows and Android smart routing
are automated-only and this residual risk is documented.

**Acceptance.** Go gate; Linux CI leak test; Windows cross-build; Android gate;
routing rule and kill-switch unit tests; data-refresh tests.

### v0.11.0 — Desktop polish

**Goal.** Make the desktop clients update and fit real networks without manual
setup.

**In scope**

- Daily stable update check, 7-day snooze, manual check; download the artifact,
  verify the published SHA-256, then prompt. Linux never auto-installs as root;
  Windows runs the installer; Android opens the APK installer.
- Windows (WinINET/WinHTTP) and GNOME `gsettings` system-proxy automation,
  saving and restoring the previous setting.
- Trusted-Wi-Fi/untrusted-network autoconnect rules on Linux and Windows; wired
  networks trusted by default; no metered auto-connect unless allowed.

**Non-goals.** No macOS, no silent install, no beta channel, no language
support.

**Acceptance.** Go gate; Windows cross-build; update-check and checksum tests;
proxy save/restore tests; network-rule tests.

### v0.12.0 — Language

**Goal.** Ship a native Persian experience on the surfaces where it matters.

**In scope**

- English default; Persian selectable in the setup wizard's first step and in
  Settings.
- Full RTL layout on Android and the Windows GUI.
- All user-facing GUI/Android strings, errors, notifications, widget and tile
  labels localized.
- Persian translations drafted by the agent and reviewed by the user; English
  remains the source of truth.
- TUI and CLI stay English.

**Non-goals.** No TUI/CLI localization, no additional languages, no docs
translation.

**Acceptance.** Go/Android gates; string-coverage test; RTL layout tests; user
translation review.

## Architecture — v0.6.0

### Components and boundaries

| Component | Responsibility |
|---|---|
| `internal/fxa` | Existing password login plus new TOTP verification and unblock-code support |
| `internal/webauth` (new) | PKCE generation, loopback callback server, Mozilla login URL, `/login/verify` exchange, Guardian token parsing |
| `internal/engine` | Account store, migration, active account, rotation, quota polling, login state machine |
| `internal/settings` | `account_rotation` and `rotation_threshold` validation and persistence |
| `internal/api` | Additive account/login commands and status fields |
| `internal/cli` | `login --browser`, `accounts ...`, headless URL printing |
| `internal/tui` | Account screen: list, active, add/remove/use, rotation |
| `internal/gui` | Account screen, browser launch, re-auth prompts |
| `android/` | Account screen, Custom Tabs, loopback browser flow, rotation UI |
| `mobile/` | Expose the same commands to the Android app |

### Browser sign-in flow

1. A client calls `login_start` with `method = "browser"` (or `accounts_add_start`).
2. The engine generates a PKCE verifier (128 chars) and S256 challenge, plus a
   random `state`, and starts a one-shot HTTP server on `127.0.0.1:0`.
3. The engine builds
   `https://vpn.mozilla.org/api/v2/vpn/login/<platform>?code_challenge=...&code_challenge_method=S256&user_agent=...&port=<port>&utm_medium=vpn-client&utm_source=kumiho`,
   where `<platform>` is `linux`, `windows` or `android`.
4. The client opens the URL (system browser, Custom Tab, or printed for
   headless). The browser handles FxA, captcha, TOTP and unblock codes.
5. Mozilla redirects to `http://127.0.0.1:<port>/?code=...&state=...`; the
   engine verifies `state`, rejects anything else, and closes the server.
6. The engine posts `{code, code_verifier}` to
   `https://vpn.mozilla.org/api/v2/vpn/login/verify`, receives `{user, token}`,
   derives the email/uid, stores the account and marks it active.
7. The client polls `login_status` until `done`, `error` or `cancelled`.

The flow times out after five minutes. Port binding failure, state mismatch,
exchange failure and missing user data map to fixed login states with readable
errors. The loopback server binds only to `127.0.0.1`, serves no external
assets, and never logs the code or token.

### Password fallback (TOTP and unblock)

- `POST /account/login` may answer `errno 125` with `verificationMethod` and
  `verificationReason`; the engine surfaces the reason and, when it is
  `unblock-code`, calls `POST /account/login/send_unblock_code` and accepts the
  code on retry.
- `verificationMethod = totp-2fa` moves the login state to `totp`; the engine
  calls the FxA TOTP verification endpoint with the six-digit code.
- Email 2FA and the existing email-link path stay unchanged.
- The login state gains `method` (`email`, `totp`, `unblock`, `2fa`) so every
  client can render the right input.

### Account store and migration

`accounts.json` is versioned and written atomically with mode 0600:

```json
{
  "version": 2,
  "active": "a1b2c3d4e5f6",
  "accounts": [
    {
      "id": "a1b2c3d4e5f6",
      "email": "user@example.com",
      "label": "Personal",
      "method": "browser",
      "browser": {
        "token": "...",
        "expires_at": 0,
        "reauth_required": false
      },
      "fxa": {
        "access_token": "...",
        "refresh_token": "...",
        "scope": "...",
        "expires_at": 0
      },
      "added_at": "2026-10-23T12:00:00Z",
      "last_used_at": "2026-10-23T12:00:00Z"
    }
  ]
}
```

- A browser account stores `browser.token`; a password account stores `fxa`.
  An account may have both after a later sign-in, but the default method is
  remembered.
- Passwords are never written.
- The file is limited to five accounts; adding a sixth returns a clear error.
- Adding an existing email replaces its tokens and label instead of creating a
  duplicate.
- Removing the active account selects the most recently used remaining account,
  or signs out when none remain.
- Migration reads `tokens.json` and `state.json`, creates one password account,
  writes `accounts.json`, and leaves `tokens.json` untouched for rollback. A
  malformed `accounts.json` is reported and never silently replaced.
- Labels default to the email; editing trims whitespace, rejects control
  characters and caps at 64 visible characters.

### Rotation and quota polling

Before a connect, when `account_rotation` is on:

1. Compute the active account's remaining quota. Unknown quota counts as
   eligible but sorts last.
2. If the active account is at or above `rotation_threshold`, use it.
3. Otherwise consider accounts with a valid token, no `reauth_required`, and
   quota at or above the threshold; choose the highest remaining, breaking ties
   by least recently used.
4. If none qualify, keep the active account when it still has quota; otherwise
   choose the highest remaining quota above zero.
5. If every account is exhausted, fail with a terminal error naming the
   accounts.
6. Expired/re-auth accounts are skipped with a notice; the connect never blocks
   on a re-auth prompt.

Rotation never switches mid-session. Changing the toggle or threshold applies to
the next connect.

While connected, a ticker reads `quota_poll_minutes` (default 15, range 1–1440)
and refreshes quota with `HEAD /api/v1/fpn/token` and the `X-Quota-*` headers,
falling back to a GET pass only when HEAD is not supported. Errors are logged
and retried with backoff; 401 marks the account `reauth_required`; 429 updates
the quota; neither disconnects the tunnel. Polling stops on disconnect.

### Interfaces

**Settings.** `account_rotation` (bool, false) and `rotation_threshold`
(int, 10, 1–50). Both apply on the next connect; changing them never reconnects.

**Control protocol.** Additive commands:

- `accounts_list` → accounts, active id, rotation and threshold.
- `accounts_add_start` → `{method, login_id, url}` for browser, or the password
  login state for password.
- `accounts_add_status` → `{step, email, error}`.
- `accounts_add_cancel`.
- `accounts_remove` → `{id}`.
- `accounts_use` → `{id}`.
- `accounts_set_rotation` → `{enabled, threshold}`.
- `login_start`, `login_status`, `login_cancel` for the active account.

The status snapshot gains an `accounts` summary and a `login` object. Existing
fields and commands keep their meaning; older clients ignore the new fields.

**CLI.** `kumiho login --browser`, `kumiho login --password`,
`kumiho accounts list|add|remove|use|rotation`. Headless browser login prints
the URL and waits; `--no-open` suppresses auto-open.

**TUI.** Account screen lists accounts, active marker, method, quota and the
rotation toggle/threshold; add and remove use the CLI-style prompts; labels stay
English.

**Windows GUI.** Account screen with the same actions; browser sign-in opens the
default browser and shows a waiting state; re-auth uses the same flow.

**Android.** Account screen with the same actions; Custom Tabs opens the URL;
the engine's loopback server completes the flow; `usesCleartextTraffic` stays
false globally and a network-security-config exception permits only
`127.0.0.1`/`localhost`.

### Security and error handling

- PKCE S256, random state, loopback-only bind, one-shot server, 5-minute
  timeout, no CORS, no external assets, no code/token logging.
- Tokens and secrets are 0600; error messages redact tokens and codes.
- A browser token with no parseable expiry is accepted and re-auth is driven by
  the first 401.
- Account file corruption is a hard error with the path and a recovery hint; it
  never wipes accounts.
- Rotation errors name the reason (no eligible account, all exhausted, all
  need re-auth) and never loop.
- Quota-poll failures are non-fatal and visible in logs, not in modal dialogs.

## Risks + rollback

| Risk | Mitigation / rollback |
|---|---|
| Mozilla's login page rejects the loopback redirect on Android | Keep password fallback; test the flow against the live page before shipping; document the fallback |
| Guardian browser token expires or cannot refresh | Parse expiry, mark `reauth_required`, prompt browser re-auth; rotation skips the account |
| Rotation is a ToS gray area | Opt-in, documented in README/PLAN §13, five-account cap, no password storage |
| Migration loses the session | Copy, do not move, `tokens.json`; keep it for one release; malformed files are reported |
| Account tokens leak | 0600 files, no passwords, redacted logs, loopback-only callback |
| IPC change breaks older clients | Additive commands/fields only; old-client fixture test |
| Scope creep inside v0.6.0 | The non-goals list is explicit; later features have their own releases |
| Automated-only acceptance misses a real auth failure | Mock integration tests plus the password fallback; no physical requirement was chosen |

Rollback for v0.6.0: turn `account_rotation` off, use the password flow, and
restore `tokens.json` if needed. Later chunks add their own flags
(`smart_routing`, `blocklists`, `auto_update`).
