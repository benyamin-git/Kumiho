# v0.11.0 Blocked-Region First Run — Design Spec

**Status:** Approved
**Date:** 2026-11-09

## Objective / why

A new user in a region where Mozilla answers HTTP 451 must be able to finish
first run — sign in, prepare a Guardian pass, connect — using one external
route (another VPN or the already-shipped relay). Once the tunnel is up,
Kumiho renews every control-plane request through its own tunnel, so the
external route is only needed again after the daemon has been off longer than
the pass lifetime. The app teaches the whole flow in place, and the relay
stays as the fallback for users who have no second VPN.

This replaces the approved v0.11.0 desktop-polish theme. Desktop polish moves
to v0.12.0 and language/RTL to v0.13.0. The roadmap spec is amended in the
same release.

## Success criteria / definition of done

1. `region_check` probes the five engine control-plane hosts plus
   `accounts.firefox.com`, classifies each as reachable, blocked or unknown,
   and is used by the Blocked region guide and `kumiho doctor`.
2. `kumiho prepare` fetches the Guardian pass, refreshes the server list and
   profile, writes a 0600 `pass.json` beside the tokens, and returns expiry
   and quota metadata without ever returning the token.
3. `connect` and watchdog redial reuse a cached pass while more than 60
   seconds remain; an expired or missing pass is fetched through the tunnel or
   relay when possible, otherwise reported as `bootstrap_required`.
4. After connect, every control-plane request (token refresh, server list,
   profile, pass renewal) goes through the local SOCKS5 tunnel; a 451 retries
   exactly once through the relay; disconnect reverts to the direct/relay
   path without rebuilding clients.
5. The Blocked region guide is reachable from first-run, Settings → Region and
   the `region_blocked` notice on all five clients. It leads with the other-VPN
   path and carries inline relay URL/token fields plus Test.
6. The handoff card shows a live countdown and restores the prepared state
   from `pass.json` after an app restart within ten minutes.
7. Password sign-in works through the relay; browser sign-in works through
   another VPN or another device; the guide teaches both and never claims the
   relay proxies the browser page.
8. Mock 451 tests cover the region check, prepare, pass file, reuse, runtime
   routing, reconnect and client rendering; a live manual check runs on this
   machine against the real `vpn.mozilla.org` 451.
9. Every client and doc listed below is updated, new screenshots are captured,
   the roadmap is amended, and v0.11.0 is released through the existing
   workflow.
10. The Go gate, race tests, Windows/Android cross-builds and the Android
    JVM/lint/connected gates are green; control protocol v1 stays
    byte-compatible; older clients ignore the new commands and error code.

## Scope

### In scope

- Engine: `RegionCheck`, `Prepare`, the persisted pass and its reuse, the
  runtime control-plane dialer, `bootstrap_required`, and the tunnel-first
  relay order.
- Additive IPC: `region_check` and `prepare` command types, their result
  payloads, and the `bootstrap_required` error code.
- CLI/TUI: `kumiho prepare`, `kumiho guide`, the `doctor` region check, the
  region-notice action, and the handoff countdown.
- Windows GUI: the Blocked region guide route, the onboarding branch, the
  Settings → Region entry, the dashboard error action, and the handoff card.
- Android phone and TV: the guide screen (ten-foot variant on TV), the setup
  branch, the Settings → Region entry, the dashboard notice action, the
  handoff card and the pass file through the facade.
- Docs, screenshots, roadmap amendment, CHANGELOG, README and release.

### Non-goals

- No hosted or public relay, no relay deployment automation, and no relay
  configuration sharing.
- No proxying of the browser sign-in page; the relay stays engine-only.
- No desktop-polish work (moves to v0.12.0) and no language/RTL work (moves to
  v0.13.0).
- No DNS, smart-routing, macOS or new third-party dependency work.
- No breaking change to control protocol v1, existing settings or user data.
- No automatic connect on network change and no Android foreground service;
  the explicit handoff plus the pass file is the designed behavior.
- No new persistent profile or server-list file; existing caches are reused.

## Architecture

### Region check

`Controller.RegionCheck(ctx)` sends unauthenticated requests in parallel to:

- `api.accounts.firefox.com`
- `oauth.accounts.firefox.com`
- `profile.accounts.firefox.com`
- `vpn.mozilla.org`
- `firefox.settings.services.mozilla.com`
- `accounts.firefox.com` (browser page)

Each host gets a 5-second timeout and the whole run is bounded at 20 seconds.
A 451 is `blocked`; any other HTTP response is `reachable`; a transport error
is `unknown`. The result carries the per-host status, the blocked-host list,
the browser-page flag, and whether a relay URL and token are configured. It
never sends tokens and never writes state.

The guide treats `unknown` as “could not check”: it shows Recheck and Continue
instead of blocking setup.

### Prepare and the pass file

`Controller.Prepare(ctx)`:

1. Rejects while a tunnel is connected (`bad_request`, “disconnect first”).
2. Requires a signed-in account.
3. Refreshes the server list through the existing Locations cache path.
4. Refreshes the profile through the existing FxA client.
5. Fetches a Guardian pass last, so a pass is never written without the rest.
6. Writes `pass.json` atomically beside `tokens.json`, mode 0600.

The file is:

```json
{
  "token": "<guardian pass>",
  "expires_at": 1794256800,
  "account_id": "user@example.com",
  "prepared_at": 1794256200
}
```

The token is never returned over IPC, logged, or placed in `state.json`. The
daemon loads the file at start, deletes it when expired or when its
`account_id` no longer matches the active account, and deletes it on logout
and account switch. Android places it in the no-backup tokens directory.

A partial failure keeps the previous state and returns an error naming the
failed step; the user keeps the other VPN on and retries.

### Pass reuse and reconnect

`Controller.pass` keeps the in-memory pass; the file is the restart bridge.
`Connect` and `redialOnce` use the in-memory pass or the file when more than
60 seconds remain. Otherwise they fetch through the normal chain (direct,
tunnel, relay). If no pass can be obtained and a previous pass existed, the
error is `bootstrap_required`; if the user has never prepared, it is the
existing `region_blocked`.

The ten-minute pass is renewed at half-life (about five minutes) through the
tunnel. A relay fetch is the fallback when the tunnel is down.

### Runtime control-plane routing

The control-plane clients stay built once in `UseBypassDialer`; no client is
rebuilt on connect. `controlPlaneDial` gains a live choice:

- Connected or proxy-only, with `c.socksSrv` non-nil: dial the target through
  the local SOCKS5 listener using the existing SOCKS5 client dialer, with the
  marked bypass dialer as the hop base and remote name resolution.
- Otherwise: use the marked bypass dialer as today.

The local SOCKS5 hop is loopback, so it cannot recurse into the control-plane
dialer. The relay wrapper stays outside the dialer: while connected the order
is tunnel, then relay on a 451; while disconnected it is direct, then relay.
`tlsplit` and TCP_NODELAY continue to apply to the returned connection.

### First-run flow and the Blocked region guide

Every client runs the same logical flow:

1. Consent.
2. Silent `region_check` after consent.
3. Nothing blocked: the existing sign-in step, no extra screen.
4. Something blocked: the Blocked region guide before sign-in.
5. The guide offers the other-VPN path first and the relay path second.
6. Other-VPN path: turn on the other VPN, sign in, return, Prepare, turn off
   the other VPN, Connect. The prepared card counts down.
7. Relay path: paste the relay URL and token, Test, sign in with a password,
   Connect. The relay handles the first blocked request; the tunnel handles
   renewals after connect.
8. A valid `pass.json` reopens the prepared card after a restart; no repeat of
   the other-VPN steps is needed within the window.

The guide is a reusable screen, not a numbered wizard step:

- GUI: a `#/blocked-region` route, linked from onboarding, Settings → Region
  and the dashboard notice.
- Android phone/TV: a Blocked region screen in the setup flow and the shell;
  the TV version is the same content in the ten-foot shell.
- CLI: `kumiho guide` prints the same steps; `kumiho prepare` performs them.
- TUI: Enter on the region notice opens a guide modal; Settings → Region also
  opens it.

The GUI health check and `kumiho doctor` add the same region result after
sign-in; the doctor's existing reachability check is corrected so a 451 is no
longer reported as merely “reachable”.

### Sign-in paths

- Password sign-in uses the engine's FxA client, so the relay wrapper can
  carry it when the direct path is blocked.
- Browser sign-in opens `accounts.firefox.com` in the user's browser. The
  relay deliberately does not proxy that page; the guide tells the user to
  use the other VPN or to sign in on another device and paste the redirect
  URL.
- The guide's copy never promises that the relay can complete browser sign-in.

### Client surfaces

- **CLI:** `kumiho guide`, `kumiho prepare [--json]`, `kumiho doctor` region
  check, `kumiho connect` guidance that names `prepare` and `guide`, and
  `kumiho status` pass expiry (already present).
- **TUI:** Enter on the region notice opens the guide modal; Settings → Region
  exposes the same entry; the handoff notice includes the countdown; the
  region error uses the warning tone, not the green notice tone.
- **Windows GUI:** the onboarding branch after consent, the `#/blocked-region`
  screen, the Settings → Region row, the dashboard notice action, the inline
  relay fields and Test, and the handoff card with the countdown.
- **Android phone:** the same guide in Compose, the setup branch after
  consent, the Settings → Region row, the dashboard notice action, the inline
  relay fields and Test, and the handoff card.
- **Android TV:** the ten-foot variant, same content and order, focusable
  cards, other VPN first, relay fields inline.

### IPC and protocol

Additive only:

- `region_check` → `RegionCheckResult`.
- `prepare` → `PrepareResult` (expiry, quota, server-list/profile refresh
  flags, relay-used flag; never the token).
- `bootstrap_required` as a new `RemoteError` code.

Control protocol v1 envelopes and existing payload bytes are unchanged.
Older clients ignore the new commands and code.

### Errors and edge cases

- No pass and no relay, after an earlier prepare: `bootstrap_required` with
  “open Blocked region and prepare again”.
- No pass and no relay, never prepared: `region_blocked` with the guide action.
- Relay configured but failing: the existing relay-failed `region_blocked`
  copy, pointing at the guide.
- Edge 451: unchanged and terminal; a control-plane relay cannot fix it.
- Prepare while connected: “disconnect first”.
- Prepare signed out: “sign in first”.
- Account switch or logout: delete the pass file; the next connect needs
  prepare.
- Clock skew: the countdown uses the daemon expiry; `doctor` keeps its clock
  check.
- Android with another VPN active at Connect: the existing VpnService consent
  path reports it; the guide tells the user to turn it off first.
- Android Always-on/lockdown: documented as a reason a later re-bootstrap may
  need lockdown disabled first.
- Preflight unknown: Recheck/Continue, never a dead end.

### Security and privacy

- The Guardian pass is a bearer token: 0600 file, atomic write, no IPC, no
  logs, deleted on expiry/logout/account switch, no Android backup.
- The relay token remains write-only; the guide's inline fields never display
  a stored token.
- Control-plane traffic through the tunnel stays TLS end-to-end; the edge sees
  the target host, not the payload. The relay sees headers and bodies when it
  is used, which the guide states.
- Region probes are unauthenticated.

## Risks + rollback

- **Edge CONNECT to `vpn.mozilla.org` may be refused.** The whole self-renewal
  idea depends on it. Test a throwaway session through the real edge before
  building the UI; if refused, keep the relay path as the primary and record
  the finding before continuing.
- **The relay request may follow the tunnel dialer.** If the tunnel's edge
  exit is blocked, the relay fallback could fail. Test the relay-on-451 path
  while connected; a direct exception for the relay host is the fallback.
- **The pass file is a secret on disk.** Roll back by deleting it and
  reverting the runtime dialer; the relay path remains.
- **Android one-VPN handoff.** The pass file survives process death; the guide
  copy carries the order. If the app is killed during the handoff, the
  prepared card restores from the file.
- **Replacing v0.11.0 delays desktop polish.** The roadmap amendment and
  CHANGELOG make the move explicit.
- **Live 451 depends on this machine.** CI uses mocks; the live check is
  manual and documented.
